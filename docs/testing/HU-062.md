# Pruebas de sincronización y red degradada — HU-062

Esta guía integra el procedimiento del manual técnico existente. Decisión técnica: [ADR-0008](../adr/0008-hu062-pruebas-e2e-red-degradada.md), propuesto para ratificación; antecedentes de implementación offline en [ADR-0007](../adr/0007-hu061-publicacion-offline-y-cache-privada.md). No se declara localizada ni aprobada la Decisión 6.

## Requisitos y aislamiento

Node 24 en PATH, Java 21, Maven, Docker accesible, imagen PostGIS y dependencias/navegador Playwright **ya disponibles**. Para fase 3 se requieren `ss` (lectura TCP_INFO) y Python 3 estándar (validación de evidencias), ambos existentes en el equipo utilizado. El script no instala paquetes, imágenes adicionales ni herramientas; Maven trabaja con `-o`. Verificar `node --version`, `java -version` y `mvn -version` antes de ejecutar.

El runner usa `hu061-aceptacion-postgis`, base `hu061_aceptacion` en tmpfs, Spring Boot en `127.0.0.1:18090` y proxy en `127.0.0.1:4173`. Estos nombres preservan el fixture real de HU-061. Si existen el contenedor o los puertos, se detiene sin reemplazarlos. Nunca apuntar estos fixtures a bases habituales, staging o producción.

El backend no carga `.env`; recibe únicamente variables ficticias de prueba y directorios exclusivos para objetos/temporales Java. Flyway conserva sus validaciones. El script etiqueta el contenedor, guarda su ID y elimina solo ese recurso al salir, junto con sus procesos y almacenamiento temporal. Conserva logs y resultados en la carpeta `/tmp/hu062-<fase>.XXXXXX` que muestra por consola.

En fase 3 se reinicia únicamente el proceso Java desechable entre lotes de suites, conservando su base y archivos, para que sus ráfagas de autenticación no compartan el presupuesto en memoria de 20 refresh por IP/minuto. No se desactiva ni se modifica ese límite. Las regresiones HU-061 de expiración mantienen su TTL de prueba de cinco segundos.

## Comandos

Desde `sgp-client`, con las herramientas seleccionadas en PATH:

```bash
bash e2e/hu061/run-hu062-fase1.sh fase1
bash e2e/hu061/run-hu062-fase1.sh fase2
bash e2e/hu061/run-hu062-fase1.sh fase3
```

El nombre del script se conserva por compatibilidad. Selecciones:

| Modo | Trabajo ejecutado |
|---|---|
| `fase1` | Dos casos: persistencia offline con recarga por worker y sincronización normal con fotos/respuestas reales. |
| `fase2` | Tres casos dos veces con contextos/proxy nuevos: latencia, fallo previo y confirmación de creación perdida; después fase 1 y cinco regresiones HU-061. El diagnóstico netem no configura red. |
| `fase3` | Un fallo deliberado de aserción para comprobar evidencias; restauración del modo normal, dos casos fotográficos y regresiones pertinentes de fases 1/2 y HU-061. No reintenta netem. |
| `regresion` | Dos recorridos reales HU-061 más tres PWA con API simulada explícita. |
| `todo` | Conserva la selección original de fase 1 + regresiones HU-061; no significa todas las fases de HU-062. |

`HU062_FASE1`, `HU062_FASE2` y `HU062_FASE3` habilitan descubrimiento selectivo; el runner las configura. No basta invocar la suite sin backend: los casos reales validan origen, identidad de base/etiqueta y almacenamiento. La selección habitual `npm run test:pwa` conserva sus casos HU-061.

## Perfiles y verificaciones

Preparación común: login real, formulario precargado, creación offline por UI, respuestas y cuatro fotografías con EXIF en categorías ACCESO/SUPERESTRUCTURA/SUBESTRUCTURA/CAUCE, publicación encolada con claves durables. Se mantiene el Service Worker real.

| Perfil | Mecanismo reproducible |
|---|---|
| Normal / offline | Proxy transparente; desconexión solo del contexto del navegador. Se verifica recarga por worker, hash de Blob, respuestas, claves y ausencia de escrituras remotas. |
| Latencia | 1500 ms antes de reenviar y 1500 ms antes de entregar cada escritura de la inspección/fotos seleccionadas. Auth/health/lecturas y shell quedan fuera. Barreras diagnósticas separadas del retardo fijo. |
| Fallos de creación | Dos envíos interrumpidos antes del backend; o respuesta perdida tras un 201 real. Cuerpo incompleto produce error de transporte observable y se comprueban los reintentos de la cola. |
| Corte fotográfico | Solo primer intento de la primera foto: metadatos y `floor(bytesBinarios/2)` enviados, sin completar multipart. Callback de escritura y TCP_INFO del socket receptor prueban recepción parcial; después se corta upstream, se pasa el navegador a offline y se restaura la conexión. |
| Confirmación fotográfica perdida | Multipart completo y 201 reales; el proxy interrumpe la entrega del JSON. El siguiente intento conserva UUID, clave, metadatos y hash de imagen; se verifica persistencia única. |
| Pérdida de paquetes | **No verificada**: requiere entorno previamente habilitado para netem, aislamiento, contadores de descartes y restauración. Ningún perfil anterior se presenta como equivalente. |

El proxy solo trata escrituras del UUID seleccionado; sus controles `__e2e` no existen en Spring Boot. Los casos esperan estados/eventos observables, nunca un sleep arbitrario para declarar sincronización terminada. La latencia nominal y las barreras se registran por separado de las duraciones del equipo; el backoff/jitter de producción se conserva.

Oráculo remoto compartido: datos correctos, una inspección adicional del autor/puente, cuatro IDs/categorías, PUBLICADA/CONFIRMADA, cola de inspección y fotos vacía, dos transiciones y un IC de publicación. Originales/miniaturas deben descargar, decodificar y coincidir con los archivos físicos. El tamaño y checksum del **JPEG normalizado** se comparan con PostgreSQL; el hash del Blob local demuestra conservación entre intentos. El inventario físico debe ser el previo más ocho objetos completos, sin archivos adicionales.

## Evidencias y falla controlada

El modo `fase3` ejecuta primero el caso de confirmación con `HU062_FALLO_CONTROLADO=true`. La aserción marcada se dispara **después** de verificar el servidor real. El script exige que sea exactamente ese fallo: no acepta otro error o una prueba omitida. Valida PNG/dimensiones, integridad ZIP y eventos de traza/red, diagnóstico de Dexie, resultado remoto PUBLICADA y cola vacía. Guarda `verificacion-evidencias.json`.

Después ejecuta la suite con `HU062_FALLO_CONTROLADO=false`; las expectativas funcionales permanecen intactas. Ese fallo deliberado se informa separado de las pruebas aprobadas. No se edita código durante captura de trazas.

Los adjuntos incluyen snapshots locales/remotos, contadores TCP de la conexión exclusiva, eventos del proxy con claves/hashes/ordinales y resultados del oráculo. Los reportes no incluyen credenciales, JWT o cookies. Las trazas pueden capturar sesiones: son privadas y no deben publicarse ni versionarse. Las carpetas `/tmp` son evidencia de la ejecución, no una dependencia para reproducirla.
